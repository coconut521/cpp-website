第9章 移动语义与智能指针

本章讲 C++11 的移动语义与智能指针：用“搬资源”取代“拷资源”，把 delete 交给对象生命周期自动完成。

学习目标

  • 用“能否取地址 / 有无名字”区分左值与右值，说清 && 绑定什么；理解 std::move 只是转成右值的类型转换。
  • 对比移动构造/移动赋值与拷贝的区别（接管指针、不复制缓冲区），说明移动后原对象处于有效但未指定状态。
  • 默写 Rule of Five（五大件）与 Rule of Zero，说明移动构造标 noexcept 的原因。
  • 使用 unique_ptr：make_unique、-> 与 *、get/release/reset 的区别。
  • 推演 shared_ptr 的 use_count 变化，用 weak_ptr 打破循环引用。
  • 用 ofstream、lock_guard 说明 RAII“构造获取、析构释放”的套路；列举裸 new/delete 的问题，知道 auto_ptr 已被 C++17 移除。

前置知识：第7章 类与对象（拷贝构造、析构函数、浅拷贝深拷贝）；第8章 继承与多态。

1. 左值与右值

一个够用的判别法：能取地址、有名字、有确定位置的，是左值；字面量、临时对象、表达式的中间结果，是右值。左值引用 T& 绑定左值；右值引用 T&&（C++11 起）绑定右值。

示例1：左值、右值与两种引用

知识点：左值 / 右值入门必会
#include <iostream>

int main() {
    int a = 10;            // a 是左值：有名字、能取地址 &a
    int& lref = a;         // 左值引用绑定左值
    // int& bad = 42;      // ⛔ 编译错误：普通左值引用不能绑定右值
    const int& cref = 42;  // 特例：const 左值引用可以绑定右值（延长其寿命）

    std::cout << a << " " << lref << " " << cref << "\n";
    std::cout << (5 + 3) << "\n";   // 5+3 是右值：表达式的临时结果
    return 0;
}
▶ 预期输出
10 10 42
8

逐行解释

  • 第4行：a 有名字、&a 合法 → 左值。42 是字面量，没有地址可取 → 右值。
  • 第6行：普通左值引用不能绑定右值。第 7 行的 const 引用是例外：只读，允许绑定临时对象。
  • 第10行：5 + 3 先算出临时结果 8，打印后即销毁——典型的右值。同理 std::string("hi") + "!"、函数按值返回的对象，都是右值。

变体对比

变量是左值，但表达式不一定：a + 1 是右值（临时结果）；a 单独出现才是左值。考试口诀：看的是“这个表达式有没有名字和地址”，不是“它是不是个变量”。

⚠ 易错点

字符串字面量 "hello" 是左值（类型 const char[6]，静态存储、可取地址）。本课程考题里按“字面量整体当右值处理”不会出错；记住临时对象和表达式结果一定是右值。

2. 右值引用 && 与 std::move

T&& 是右值引用，用来绑定右值。std::move(x) 只做一件事：把左值 x 转换成右值（一个类型转换，cast）。它本身不清空、不释放任何东西——真正的移动发生在随后被选中的移动构造/移动赋值里。

示例2：std::move 之后原对象不变

知识点：std::move 的本质高频考点经典陷阱
#include <iostream>
#include <string>
#include <utility>

void which(std::string& s)  { std::cout << "左值引用版本: " << s << "\n"; }
void which(std::string&& s) { std::cout << "右值引用版本: " << s << "\n"; }

int main() {
    std::string a = "hello";
    which(a);                    // 左值 → 左值引用版本
    which(std::string("temp"));  // 临时对象（右值）→ 右值引用版本
    which(a + " world");         // 表达式结果是右值
    which(std::move(a));         // std::move 把 a 转成右值 → 选中右值引用版本
    std::cout << "a 仍在，值有效: " << a << "\n";
    return 0;
}
▶ 预期输出
左值引用版本: hello
右值引用版本: temp
右值引用版本: hello world
右值引用版本: hello
a 仍在，值有效: hello

逐行解释

  • 第5~6行：一对重载分别绑定左值引用与右值引用，重载决议按实参是左值还是右值选择。
  • 第13行：std::move(a) 把左值 a 转成右值 → string&& 版本被选中，仅此而已。
  • 第14行：关键证据——a 仍是 "hello"，因为 which 只是绑定了引用，没有从中移动。std::move 本身不动任何数据。
  • 真正发生移动是在“右值去初始化/赋值另一个对象”时：比如 std::string b = std::move(a); 会选中 string 的移动构造——那一步才把 a 的内部缓冲区偷走（示例 3、4）。

变体对比

把第 13 行改成 std::string b = std::move(a);：这次移动构造真的发生，a 的缓冲区被接管（示例 4 演示其状态）。move 只是把对象标记为可移动；实际移动由接下来的构造/赋值完成。

⚠ 易错点

判断题“std::move 会把对象的内容搬走”为假。它只是 cast（实现上就是 static_cast<T&&>），标准里甚至没有“move 函数移动了什么”这回事。

std::move(x) 只是宣布 x 可被移动。移动本身由移动构造/移动赋值执行；在那之前，x 照常能用。

3. 移动构造与移动赋值

拷贝构造做深拷贝：分配一块新内存，把内容逐个元素复制过来。移动构造只做一件事：接管源对象的内部指针，再把源对象置为空状态——成本是常数次指针操作，O(n) 次元素复制归零。

示例3：Buffer 的拷贝构造 vs 移动构造

知识点：移动构造高频考点
#include <iostream>
#include <cstring>
#include <utility>

class Buffer {
public:
    explicit Buffer(size_t n) : size_(n), data_(new int[n]) {
        std::cout << "构造：分配 " << n << " 个 int\n";
    }
    Buffer(const Buffer& other)                       // 拷贝构造：深拷贝
        : size_(other.size_), data_(new int[other.size_]) {
        std::memcpy(data_, other.data_, size_ * sizeof(int));
        std::cout << "拷贝构造：复制了 " << size_ << " 个元素\n";
    }
    Buffer(Buffer&& other) noexcept                   // 移动构造：偷指针
        : size_(other.size_), data_(other.data_) {
        other.data_ = nullptr;   // 掏空对方，防止双重释放
        other.size_ = 0;
        std::cout << "移动构造：只偷走了指针，0 次元素复制\n";
    }
    ~Buffer() { delete[] data_; }   // 各自 delete 自己的指针，互不干扰
private:
    size_t size_;
    int*   data_;
};

int main() {
    Buffer a(1000);
    Buffer b = a;             // 拷贝构造
    Buffer c = std::move(a);  // 移动构造：std::move 把 a 转成右值
    return 0;                 // 析构顺序 c → b → a，各自清理各自的
}
▶ 预期输出
构造：分配 1000 个 int
拷贝构造：复制了 1000 个元素
移动构造：只偷走了指针，0 次元素复制

逐行解释

  • 第29行：b = a 中 a 是左值 → 选中拷贝构造：new 一块新内存 + 逐元素复制。两个对象各有一份完整数据。
  • 第30行：std::move(a) 把 a 转成右值 → 选中移动构造：只把 data_ 指针抄给 c，然后让 a 的 data_ = nullptr。缓冲区从头到尾只有一份，只是换了主人。
  • 第17行：noexcept 承诺“移动不抛异常”。std::vector 扩容搬元素时，只有 noexcept 的移动构造才会被采用（搬一半抛异常无法回滚）；否则 vector 退回用拷贝，移动优化失效。
  • 第31行：c、b、a 依次析构，各自 delete[] 自己的指针：a 是空壳、b 是副本、c 是原缓冲区——无泄漏、无双重释放。

变体对比

移动赋值同理：c = std::move(b); 会先释放 c 原来的资源，再把 b 的指针偷过来。拷贝构造 + 拷贝赋值 + 移动构造 + 移动赋值 + 析构，就是下一节的“五大件”。

⚠ 易错点

移动构造里必须把源对象的指针置空，否则两个对象析构时对同一块内存 delete[] 两次——未定义行为（本章示例 11）。

示例4：被移动后的对象处于“有效但未指定”状态

知识点：移动后状态高频考点
#include <iostream>
#include <string>
#include <utility>

int main() {
    std::string s1 = "hello";
    std::string s2 = s1;               // 拷贝构造：s1 保持 "hello"
    std::string s3 = std::move(s1);    // 移动构造：s1 被掏空

    std::cout << "s2 = " << s2 << "\n";
    std::cout << "s3 = " << s3 << "\n";
    // ⚠ 此刻不要读 s1 的值：标准只保证它"有效但未指定"
    s1 = "reborn";                     // 但可以析构、可以重新赋值
    std::cout << "s1 = " << s1 << "\n";
    return 0;
}
▶ 预期输出
s2 = hello
s3 = hello
s1 = reborn

逐行解释

  • 第8行：移动构造真的发生（与示例 2 不同）：s3 接管了 s1 的内部缓冲区，s3 的值就是原来的 "hello"。
  • 第12行：s1 被移动后处于有效但未指定状态——“有效”= 能析构、能赋新值、能调用无前提要求的成员函数；“未指定”= 它的值标准不承诺（通常是空串，但别依赖）。
  • 第14行：给 s1 赋新值完全合法，赋完一切如常。本例因此不打印被移动后的 s1。

⚠ 易错点

“被移动的 string 一定是空串”是错误说法——那是常见实现的巧合，不是标准承诺。考试问“移动后还能做什么”，答：析构、赋新值、调用无前置条件的成员函数；不能答“读它的值”。

4. Rule of Five 与 Rule of Zero

第 7 章的“三大件”（析构、拷贝构造、拷贝赋值）在 C++11 后升级为五大件：一旦你因为管理资源手写了其中任何一个，另外四个的默认行为多半就不对了，要成套考虑。

示例5：五大件长什么样（片段）

知识点：Rule of Five / Rule of Zero
// Rule of Five（片段）：只要手动管理资源（写了析构函数），
// 下面五个特殊成员就要成套考虑 —— 简称"五大件"
class Buffer {
public:
    Buffer(size_t n);                           // 普通构造（不算五大件）
    ~Buffer();                                  // ① 析构函数
    Buffer(const Buffer& other);                // ② 拷贝构造
    Buffer& operator=(const Buffer& other);     // ③ 拷贝赋值
    Buffer(Buffer&& other) noexcept;            // ④ 移动构造
    Buffer& operator=(Buffer&& other) noexcept; // ⑤ 移动赋值
private:
    int*   data_;
    size_t size_;
};

// Rule of Zero：不手写任何资源管理代码 ——
// 成员用 std::vector / std::string / std::unique_ptr 托管，
// 五大件一个都不写，编译器生成的默认版本恰好全对。
class Document {
    std::string title_;                 // 自会拷贝、自会移动、自会释放
    std::vector<int> data_;
};

逐条解释

  • 为什么成套：手写析构通常意味着浅拷贝会双重释放（第 7 章示例 9）；而一旦声明了拷贝构造，编译器不再隐式生成移动版本——std::move 会静默退化成拷贝。
  • 不想拷贝就删掉：Buffer(const Buffer&) = delete;（C++11 起）直接禁用拷贝，比 C++98 的“声明为 private 且不实现”清楚得多。
  • Rule of Zero 是默认答案：本课程写类时，除非题目明确要求管理裸资源，否则一律用容器和智能指针托管成员——零手写、零泄漏、零双重释放。

⚠ 易错点

判断题“写了析构函数就该把五个特殊成员都写齐”对资源管理类成立；但对“根本不管理资源的普通类”，什么都不写（Rule of Zero）才是正解。Rule of Five 说的是“要考虑”，不是“都要手写”——用 = default 显式表态也算数。

考试简答题模板：“为什么移动构造要标 noexcept？”——vector 等容器扩容搬移元素时，为保证异常安全，只有 noexcept 的移动构造才会被采用；否则退回拷贝，性能优化失效。

5. unique_ptr：独占所有权的智能指针

std::unique_ptr<T> 独占一个堆对象：出作用域（或被 reset）时自动销毁管理的对象。它不能拷贝（拷贝意味着两个主人、双重释放），只能移动：所有权随之转移。

示例6：make_unique、-> 与 *、所有权转移

知识点：unique_ptr高频考点C++14
#include <iostream>
#include <memory>
#include <string>
#include <utility>

class Cat {
public:
    explicit Cat(std::string name) : name_(std::move(name)) {
        std::cout << name_ << " 出生\n";
    }
    ~Cat() { std::cout << name_ << " 离开\n"; }
    const std::string& name() const { return name_; }
    void meow() const { std::cout << name_ << "：喵\n"; }
private:
    std::string name_;
};

int main() {
    auto p = std::make_unique<Cat>("咪咪");   // C++14 起推荐的创建方式
    p->meow();                                 // 用 -> 访问成员
    std::cout << "它叫 " << (*p).name() << "\n";  // 用 * 解引用

    // std::unique_ptr<Cat> q = p;            // ⛔ 编译错误：不能拷贝（独占！）
    auto q = std::move(p);                     // ✅ 只能移动：所有权 p → q
    std::cout << "p 现在是 " << (p ? "非空" : "空") << "\n";
    return 0;                                  // q 离开作用域：自动 delete
}
▶ 预期输出
咪咪 出生
咪咪：喵
它叫 咪咪
p 现在是 空
咪咪 离开

逐行解释

  • 第19行：make_unique<Cat>("咪咪") 在堆上构造 Cat 并立刻交给 unique_ptr 管理——全程没有出现裸 new，不会忘记释放，异常时也不泄漏。
  • 第20~21行：p->meow() 与裸指针手感完全相同；(*p).name() 演示 * 解引用拿到对象本身。
  • 第23行：注释掉的那行是编译错误——unique_ptr 的拷贝构造被 = delete，所有权必须唯一。
  • 第24行：std::move(p) 走移动构造：q 接管 Cat，p 变成空指针，所以打印“空”。第 27 行 q 离开作用域自动 delete，“咪咪 离开”就是析构输出——全程没有手写 delete。

变体对比：数组特化

管理动态数组用 std::unique_ptr<int[]> arr = std::make_unique<int[]>(10);：用 arr[i] 访问元素，析构时自动用 delete[] 而不是 delete。

⚠ 易错点

unique_ptr 转移所有权后，旧指针立即变空；再用旧指针（p->meow()）就是对空指针解引用，运行时崩溃。

示例7：get / release / reset 的区别

知识点：get / release / reset高频考点
#include <iostream>
#include <memory>

int main() {
    auto p = std::make_unique<int>(42);

    int* raw = p.get();            // get：取裸指针，所有权仍归 p
    std::cout << "get 后 *raw = " << *raw << "，p 非空? " << (p ? "是" : "否") << "\n";

    int* released = p.release();   // release：交出所有权，p 变空
    std::cout << "release 后 p 非空? " << (p ? "是" : "否")
              << "，*released = " << *released << "\n";
    delete released;               // 调用方必须自己 delete，否则泄漏

    p = std::make_unique<int>(7);
    p.reset();                     // reset：立即销毁管理的对象，p 变空
    std::cout << "reset 后 p 非空? " << (p ? "是" : "否") << "\n";
    return 0;
}
▶ 预期输出
get 后 *raw = 42，p 非空? 是
release 后 p 非空? 否，*released = 42
reset 后 p 非空? 否

逐行解释

  • get()：只借不拿。返回裸指针给外部“看一眼”，所有权仍在 p 手里，p 不变空，p 析构时照常释放。绝不许把 get 的结果拿去 delete——那会和 p 构成双重释放。
  • release()：只还不销毁。交出所有权、自己变空，把“删除责任”移交给调用方：所以第 13 行必须 delete released。典型用途是把托管对象交给某个只收裸指针的旧接口。
  • reset()：立刻销毁。当场 delete 管理的对象（无参调用即“现在就空”）；也可 reset(newPtr) 换一个管。三兄弟记忆：get 借、release 交、reset 销。

变体对比

bool 判断 (p ? ... : ...) 用的不是比较，是 unique_ptr 的显式转换：有对象为 true，空为 false。判断“还管不管着东西”就问它本身。

⚠ 易错点

release 之后忘记 delete 返回的指针 = 内存泄漏；delete 之后还写 *released = 悬空指针解引用（UB）。

6. shared_ptr：引用计数的共享所有权

std::shared_ptr<T> 允许多个指针共同拥有同一个对象。内部有一个隐藏的控制块记录引用计数：拷贝一次 +1，析构一次 -1，计数归零的那一刻销毁对象。

示例8：use_count 的变化

知识点：引用计数高频考点
#include <iostream>
#include <memory>
#include <string>
#include <utility>

class Res {
public:
    explicit Res(std::string tag) : tag_(std::move(tag)) {
        std::cout << tag_ << " 构造\n";
    }
    ~Res() { std::cout << tag_ << " 析构\n"; }
private:
    std::string tag_;
};

int main() {
    std::shared_ptr<Res> a = std::make_shared<Res>("资源R");
    std::cout << "创建 a 后 use_count = " << a.use_count() << "\n";
    {
        std::shared_ptr<Res> b = a;      // 拷贝：计数 +1
        std::cout << "拷贝出 b 后 use_count = " << a.use_count() << "\n";
        std::shared_ptr<Res> c = a;      // 再 +1
        std::cout << "拷贝出 c 后 use_count = " << a.use_count() << "\n";
    }                                    // b、c 离开作用域：各 -1
    std::cout << "离开作用域后 use_count = " << a.use_count() << "\n";
    return 0;                            // a 析构：计数归零 → 资源销毁
}
▶ 预期输出
资源R 构造
创建 a 后 use_count = 1
拷贝出 b 后 use_count = 2
拷贝出 c 后 use_count = 3
离开作用域后 use_count = 1
资源R 析构

逐行解释

  • 第17行：make_shared 把“对象本体”和“控制块”一次性分配好（比 shared_ptr<Res>(new Res) 更快也更安全），a 是第一个持有者，计数 1。
  • 第20、22行：每拷贝一个 shared_ptr，控制块计数 +1。b、c、a 是三个不同的指针变量，但它们指向同一个 Res 对象。
  • 第24行：内层作用域结束，b、c 按声明的反序析构，计数 3→2→1。计数没归零，Res 活着。
  • 第26行：main 结束，最后一个持有者 a 析构，计数 1→0——此刻才执行 ~Res，打印“资源R 析构”。析构打印永远出现在计数归零之后。

⚠ 易错点

同一个裸指针初始化两个 shared_ptr（shared_ptr<Res> p1(raw); shared_ptr<Res> p2(raw);）不是“共享”，是两套独立计数管同一块内存——析构时双重释放。要共享就永远从已有的 shared_ptr 拷贝。

线程安全一句话：不同线程操作指向同一控制块的多个 shared_ptr 副本时，计数增减是原子操作（C++11 起保证）；但多个线程同时读写同一个 shared_ptr 对象本身仍需加锁——计数安全，指针本身不安全。

7. 循环引用与 weak_ptr

引用计数有个问题：两个对象用 shared_ptr 互相持有时，外部的指针全消失后，两个计数各剩 1，永远到不了 0，谁也不析构——这就是循环引用导致的内存泄漏。std::weak_ptr 只观察对象、不增加强计数，可用来打破循环。

示例9：循环引用导致析构不执行

知识点：循环引用 / weak_ptr高频考点
#include <iostream>
#include <memory>
#include <string>

struct Person {
    std::string name;
    std::shared_ptr<Person> partner;   // 强引用：会把对方"撑住"
    ~Person() { std::cout << name << " 析构\n"; }
};

int main() {
    auto a = std::make_shared<Person>();
    auto b = std::make_shared<Person>();
    a->name = "A";
    b->name = "B";
    a->partner = b;    // b 的计数 1→2
    b->partner = a;    // a 的计数 1→2
    std::cout << "a.use_count = " << a.use_count() << "\n";
    std::cout << "b.use_count = " << b.use_count() << "\n";
    std::cout << "main 结束：注意下面没有任何析构输出 —— 泄漏！\n";
    return 0;
}
▶ 预期输出
a.use_count = 2
b.use_count = 2
main 结束：注意下面没有任何析构输出 —— 泄漏！

逐行解释

  • 第16~17行：互指之后每个对象被两处强持有（局部变量 + 对方的 partner），计数都是 2。
  • main 结束：局部 a、b 按反序析构，A 的计数 2→1（B.partner 还持有），B 同理。计数永远到不了 0，两个 ~Person 都不会执行——输出里没有析构行，这就是泄漏。
  • 修复：把其中一方的 partner 改成 std::weak_ptr<Person>。weak_ptr 只观察不撑计数；要用时 partner.lock() 临时升级成 shared_ptr（对象已死则得到空），配 expired() 判断是否还在。

变体对比：partner 改成 weak_ptr 之后

#include <iostream>
#include <memory>
#include <string>

struct Person {
    std::string name;
    std::weak_ptr<Person> partner;   // 弱引用：只观察，不撑计数
    ~Person() { std::cout << name << " 析构\n"; }
};

int main() {
    auto a = std::make_shared<Person>();
    auto b = std::make_shared<Person>();
    a->name = "A";
    b->name = "B";
    a->partner = b;   // 不增加 b 的强计数
    b->partner = a;   // 不增加 a 的强计数
    std::cout << "a.use_count = " << a.use_count() << "\n";   // 1
    std::cout << "b.use_count = " << b.use_count() << "\n";   // 1
    return 0;
}

预期输出：

a.use_count = 1
b.use_count = 1
B 析构
A 析构

每个对象只剩局部变量一个强持有（计数 1）。main 结束时局部变量按声明反序析构：先 b（B 计数 1→0，“B 析构”），再 a（“A 析构”）。

⚠ 易错点

weak_ptr 不能直接解引用（*partner 不存在）——必须 lock() 拿到临时 shared_ptr 才能用，这是防悬空的设计。设计双向关系（父/子、夫妻、观察者）时，“一方强、一方弱”是固定套路。

8. RAII：资源获取即初始化

前面所有工具共享同一个思想——RAII（Resource Acquisition Is Initialization，资源获取即初始化）：获取资源放在构造函数里，释放资源放在析构函数里，让资源生命周期与对象生命周期绑定。栈上对象一定会析构（哪怕中途抛异常、栈展开时也照析构），所以资源一定会释放。文件、锁、内存都适用这一模式。

示例10：ofstream 管文件，lock_guard 管锁——同一套路

知识点：RAII工程必备
#include <iostream>
#include <fstream>
#include <mutex>

int findAnswer() { return 42; }

void writeFile() {
    std::ofstream out("answer.txt");            // 构造 = 打开文件（获取资源）
    out << "answer = " << findAnswer() << "\n";
}                                               // out 析构 = 自动关闭文件

std::mutex g_mutex;
int g_counter = 0;

void addCounter() {
    std::lock_guard<std::mutex> lock(g_mutex);  // 构造 = 加锁
    g_counter += findAnswer();
}                                               // lock 析构 = 自动解锁

int main() {
    writeFile();
    addCounter();
    std::cout << "counter = " << g_counter << "\n";
    return 0;
}
▶ 预期输出
counter = 42

逐行解释

  • 第8~10行：ofstream 在构造时打开文件，函数结束时自动关闭——全程没有 close、没有异常泄漏。若第 9 行中途抛异常，栈展开仍会析构 out，文件照样关好。
  • 第16~18行：lock_guard 构造时加锁、析构时解锁，忘记解锁的典型多线程 bug 因此不会发生。
  • 统一套路：文件（ofstream/fstream）、锁（lock_guard/unique_lock）、内存（unique_ptr/shared_ptr）、甚至网络连接——全是“构造获取、析构释放”。unique_ptr 就是“内存版的 lock_guard”。
  • 为什么异常时也对：C++ 保证异常传播路径上的局部对象被逐个析构（栈展开）。RAII 释放逻辑写对了，异常安全随之得到保证。

变体对比

C 风格写法 FILE* f = fopen(...); ... fclose(f); 中间任何一处 return 或抛异常，fclose 就被跳过。RAII 版本无论有几条退出路径，都只有一份释放代码——藏在析构函数里，人写不写都会执行。

⚠ 易错点

简答题把 RAII 翻译成“在初始化列表里 new”就错了。关键词是“资源的获取与释放绑定到对象的构造与析构”——初始化只是获取资源的时机，核心是对象生命周期兜底。

9. 裸 new/delete 的问题：为什么现代 C++ 不再手写

示例11：泄漏、双重释放、悬空指针

错误示范高频考点
#include <iostream>

int main() {
    // 问题1：忘记 delete → 内存泄漏
    int* leak = new int(1);

    // 问题2/3：双重释放与悬空指针（UB，切勿真的这样写）
    int* q = new int(2);
    int* alias = q;            // 两个指针指向同一块内存
    delete q;
    // delete alias;           // ⛔ 同一块内存 delete 两次：未定义行为
    // std::cout << *alias;    // ⛔ 悬空指针解引用：同样是未定义行为

    std::cout << "裸指针时代：new 与 delete 必须人肉配对\n";
    delete leak;               // 这次记得了，真实工程里经常忘
    return 0;
}
▶ 预期输出（仅指本例按注释安全运行的输出）
裸指针时代：new 与 delete 必须人肉配对

逐行解释

  • 问题1（泄漏）：new 出来的内存没有归属者，函数一结束指针消失，内存再也找不到、无法释放。
  • 问题2（双重释放）：同一块内存 delete 两次，堆管理结构被破坏。
  • 问题3（悬空指针）：delete 之后指针的值还在，但指向的内存已经归还——再用就是解引用悬空指针。
  • 根治：用 unique_ptr 管独占、shared_ptr 管共享——释放逻辑写进析构函数，自动执行。

⚠ 其中两个是未定义行为

双重释放与悬空指针解引用都是未定义行为：程序可能崩溃（glibc 下常见 double free or corruption）、可能静默算错、可能看起来一切正常——标准不规定结果，本例代码里它们被注释掉正是因此，考试也不会（不应）考它们的“输出”。内存泄漏不是 UB（行为有定义，只是资源浪费），但同样是必须消灭的 bug。

变体对比：同样的需求，现代写法

#include <iostream>
#include <memory>

int main() {
    auto p = std::make_unique<int>(10);   // 出作用域自动释放，忘不掉
    std::cout << *p << "\n";
    return 0;                             // 无需 delete：p 析构自动回收
}

11. 常见错误

1. 把 std::move 当“移动指令”——它只是转右值的 cast；移动后原对象有效但未指定。修复：move 后只析构或重赋值，不读它的值。
2. 移动构造忘写 noexcept——vector 扩容悄悄退回拷贝，性能优化静默失效。修复：资源管理类的移动构造/移动赋值一律 noexcept。
3. 双重释放 / 悬空指针——同一块内存 delete 两次、delete 后继续解引用，都是未定义行为（示例 11）；get() 拿到的指针绝不能 delete。修复：不手写 new/delete，交给智能指针。
4. 用同一裸指针初始化两个 shared_ptr——两套计数管同一块内存，析构即双重释放。修复：要共享就永远从已有 shared_ptr 拷贝，创建用 make_shared。
5. shared_ptr 循环引用泄漏——双向互指导致计数永不归零。修复：一方改 weak_ptr，“一方强、一方弱”。
6. release() 之后忘了 delete 返回的指针——所有权已移交，不删就是泄漏。修复：能不 release 就不 release；用了就立即接管。

更多同类错误见 编译错误博物馆（如“cannot bind rvalue to lvalue reference”），以及 考试易错点 中的“移动语义与智能指针”专题。

本章小结

std::move 不移动（它只是转右值的许可）；unique_ptr 独占、shared_ptr 共享、weak_ptr 观察；资源释放交给析构函数（RAII），人就不需要记得 delete。
  • 左值有名字可取地址，右值是字面量/临时/表达式结果；&& 绑定右值。
  • 移动构造 = 偷指针 + 掏空源对象；源对象此后有效但未指定；noexcept 才能被 vector 信任。
  • Rule of Five：管资源就成套考虑五大件；Rule of Zero：交给容器和智能指针，一个都不写。
  • unique_ptr：make_unique 创建、不能拷贝只能移动、get 借 / release 交 / reset 销；数组用 unique_ptr<T[]>。
  • shared_ptr：make_shared、拷贝 +1 / 析构 -1 / 归零销毁；计数增减线程安全，指针本身不是。
  • 循环引用靠 weak_ptr 打破；RAII 覆盖文件/锁/内存且异常安全；auto_ptr 已在 C++17 移除。

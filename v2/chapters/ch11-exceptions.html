第11章 异常与错误处理

很多错误只有运行时才会发生（构造函数连返回值都没有）。异常（exception）把错误打包成对象，沿调用链向上传播，直到被某个 catch 接住；配套的 RAII 保证任何退出路径都释放资源。

学习目标

  • 写 throw / try / catch，掌握 catch 按类型匹配、自上而下取第一个命中的规则。
  • 解释为什么用 const 引用捕获异常（避免对象切片、支持多态）。
  • 默画标准异常层次（std::exception → logic_error / runtime_error），使用 .what()。
  • 推演栈展开：局部对象按构造逆序析构，try 块内的对象在进入 catch 之前析构。
  • 理解 RAII 与异常安全：裸 new 在异常路径会泄漏，unique_ptr / 局部对象不会。
  • 区分 assert（调试期）、static_assert（编译期）与异常的适用时机，理解 noexcept 的语义；未捕获异常 → std::terminate，析构函数不让异常逃出，构造函数失败就抛异常。

前置知识：第1章 变量与基本类型；第7章 类与析构函数、第9章 智能指针、第10章 vector::at()（会抛 out_of_range）。

1. 三种错误处理方式

方式适用时机特点
返回错误码（如 bool ok = load(...);）预期内、常见的失败简单直接，但调用方可能忘记检查
assert 断言开发期检查“不可能发生的内部逻辑”发布版整体关闭（NDEBUG），不是给用户的报错手段
异常 throw异常的、本地处理不了的失败不能被忽略：没人接住就 std::terminate；构造函数报错的唯一手段

本章的主角是第三种。先看最小完整流程。

2. throw / try / catch：基本流程

示例1：抛出与捕获

知识点：throw / try / catch入门必会
#include <iostream>
#include <stdexcept>    // 标准异常类都住在这里

double divide(int a, int b) {
    if (b == 0)
        throw std::runtime_error("除数不能为 0");  // 抛出：函数立即退出
    return static_cast<double>(a) / b;
}

int main() {
    std::cout << divide(9, 3) << "\n";      // 正常路径
    try {
        std::cout << divide(7, 0) << "\n";  // 内部抛异常：这行没有输出完
        std::cout << "这行永远执行不到\n";   // 异常已经跳去 catch
    } catch (const std::runtime_error& e) { // 按类型匹配
        std::cout << "捕获: " << e.what() << "\n";
    }
    std::cout << "程序继续正常运行\n";       // catch 处理完接着走
    return 0;
}
▶ 预期输出
3
捕获: 除数不能为 0
程序继续正常运行

逐行解释

  • 第6行：throw 一个异常对象（这里构造 std::runtime_error）。throw 之后的语句不会执行，函数立即退出。
  • 第13行：divide(7, 0) 内部抛出异常，<< "\n" 根本没机会执行——所以第一行只输出 3，没有第二行的数字。
  • 第15行：catch 按异常的动态类型匹配：runtime_error 正好命中。匹配从上到下逐个尝试，取第一个命中的。
  • 第16行：e.what() 返回构造异常对象时给的那句话，类型是 const char*。
  • 第18行：异常被处理后，程序从 catch 之后继续。

变体对比

如果 divide 抛出的类型没有任何 catch 能接住（比如抛 int 而只有 catch (const std::exception&)），异常会继续向上传播，出了 main 还没人接 → std::terminate 终止程序（见第 6 节）。

⚠ 易错点

判断题“throw 之后函数返回默认值继续执行”——错，throw 就是“非正常返回”：本函数立即中断，控制权交给调用链上游的 catch。

3. catch 按类型匹配：派生类在前，const 引用捕获

两条铁律：① catch 自上而下逐个尝试，执行第一个匹配的，后面的不再看（不是挑“最精确”的）；② 派生类的 catch 必须写在基类前面，否则永远轮不到它。捕获一律写 const 引用。

示例2：catch 的匹配顺序与基类兜底

知识点：catch 匹配顺序高频考点
#include <iostream>
#include <stdexcept>
#include <vector>

int main() {
    try {
        std::vector<int> v = {1, 2, 3};
        v.at(10);                          // 抛 out_of_range（logic_error 的派生类）
    } catch (const std::out_of_range&) {   // 派生类 catch 放在基类前面
        std::cout << "越界异常\n";         // ← 命中这里
    } catch (const std::logic_error&) {
        std::cout << "逻辑类异常\n";       // 不执行：上面已经接住
    } catch (const std::exception&) {
        std::cout << "其他标准异常\n";     // 兜底
    }

    try {
        throw std::invalid_argument("参数不合法");
    } catch (const std::out_of_range&) {
        std::cout << "越界异常\n";         // invalid_argument 不是 out_of_range，不匹配
    } catch (const std::exception& e) {    // 基类 catch 也能接住派生类异常
        std::cout << "基类兜底: " << e.what() << "\n";
    }
    return 0;
}
▶ 预期输出
越界异常
基类兜底: 参数不合法

逐行解释

  • 第8~10行：v.at(10) 抛 out_of_range；第一个 catch 类型正中，输出“越界异常”。注意 v 本身也在进入 catch 前被析构了（栈展开机制见示例 4）。
  • 第11~14行：顺序无关的“就近原则”——一旦第一个 catch 命中，后面的 logic_error、exception 分支不再尝试。
  • 第18~22行：invalid_argument 不是 out_of_range（两者是 logic_error 下的平级派生类），第一个分支跳过；基类 exception 的 catch 接住派生类异常——引用让 e.what() 仍表现出派生类的行为（多态）。

变体对比

把第一个 try 的 catch 顺序反过来（exception 放最前）：编译器常给出“此 catch 永远不会匹配”的警告，out_of_range 分支成死代码——类型都能被基类截走。

⚠ 易错点

catch 匹配不看“像不像”，只看类型：catch (const char*) 接不住 std::string 异常。而且所有标准异常都派生自 std::exception，想兜底就 catch 它。

❌ 按值捕获：对象切片

try {
    throw std::out_of_range("x");
} catch (std::exception e) {
    // e 是“复制的基类对象”：
    // 派生类部分被切掉（切片），
    // 多态失效，多一次拷贝
}

✅ const 引用捕获：无切片、多态

try {
    throw std::out_of_range("x");
} catch (const std::exception& e) {
    // e 绑定到原异常对象：
    // 无拷贝、无切片，
    // what() 走虚函数（多态）
}

4. 标准异常层次与 .what()

所有标准异常都派生自 std::exception（<stdexcept> / <exception>），提供虚函数 what()。考试要能默画这棵树：

std::exception                    ← 所有标准异常的基类（提供 what()）
├─ std::logic_error               ← 写代码时本可避免的逻辑错误
│   ├─ std::invalid_argument      ← 无效参数（如 stoi("xyz")）
│   ├─ std::out_of_range          ← 越界（vector::at、map::at、stoi 数值超界）
│   └─ std::length_error          ← 超出最大允许长度
└─ std::runtime_error             ← 只有运行时才能发现的错误
    ├─ std::overflow_error        ← 算术溢出
    └─ std::range_error           ← 结果超出合理范围
另外两个常客：std::bad_alloc（new 分配失败）和 std::bad_cast（dynamic_cast 引用版失败），它们直接派生自 exception。

示例3：标准库替你抛的异常——stoi

知识点：invalid_argument
#include <iostream>
#include <string>
#include <stdexcept>

int main() {
    try {
        int n = std::stoi("12abc");   // 尽力解析：读到 12 为止
        std::cout << n << "\n";
        int m = std::stoi("xyz");     // 一个数字都读不到
        std::cout << m << "\n";       // 不会执行
    } catch (const std::invalid_argument&) {
        std::cout << "invalid_argument：内容不是数字\n";
    } catch (const std::exception&) {
        std::cout << "其他异常\n";
    }
    return 0;
}
▶ 预期输出
12
invalid_argument：内容不是数字

逐行解释

  • 第7~8行：stoi("12abc") 解析到第一个非数字字符就停，返回 12——不抛异常（“尾部有垃圾”不算失败）。
  • 第9行：stoi("xyz") 一个数字都没有 → 抛 invalid_argument；第 10 行永远执行不到。
  • 本例打印的是自定义消息而不是 e.what()——因为标准库抛的异常，what() 的具体文字由编译器实现决定（g++ 和 MSVC 完全不同），不能当“预期输出”。自己 throw 的消息才是确定的。

变体对比

stoi("99999999999999999999") 抛的是另一个类：std::out_of_range（数值超出 int 范围）。同类错误可能抛不同层次，所以最终兜底常用 catch (const std::exception&)。

⚠ 易错点

第 10 章的 vector::at 抛 out_of_range、本章 stoi 抛 invalid_argument——它们都是 logic_error 的派生类，都可以被 catch (const std::logic_error&) 一并接住。

5. 栈展开（重点）

异常从 throw 点向外传播时，会逐层退出沿途所有作用域；每退出一层，该层的局部对象就被按构造的逆序析构。这个过程叫栈展开（stack unwinding）。两个必考细节：被跳过的语句不执行；try 块内的对象在进入 catch 处理器之前析构。

示例4：三层调用 + 析构打印，推演栈展开顺序

知识点：栈展开高频考点易错
#include <iostream>
#include <stdexcept>

struct Guard {
    const char* name;
    explicit Guard(const char* n) : name(n) {
        std::cout << "构造 " << name << "\n";
    }
    ~Guard() { std::cout << "析构 " << name << "\n"; }
};

void inner() {
    Guard g1("inner 局部对象");
    throw std::runtime_error("boom");   // 栈展开从这里开始
}

void middle() {
    Guard g2("middle 局部对象");
    inner();
    std::cout << "middle 正常结束\n";   // 不会执行
}

int main() {
    try {
        Guard g3("try 块局部对象");
        middle();
        std::cout << "try 块正常结束\n"; // 不会执行
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << "\n";
    }
    std::cout << "程序继续\n";
    return 0;
}
▶ 预期输出
构造 try 块局部对象
构造 middle 局部对象
构造 inner 局部对象
析构 inner 局部对象
析构 middle 局部对象
析构 try 块局部对象
捕获: boom
程序继续

逐行解释

  • 构造顺序：进入 try 块先构造 g3 → 进入 middle 构造 g2 → 进入 inner 构造 g1。
  • 第14行 throw 之后：栈展开开始——先退出 inner（析构 g1），再退出 middle（析构 g2）。两处“正常结束”的 cout 都被跳过。
  • 最关键一行：异常退出 try 块时，g3 也被析构——发生在进入 catch 处理器之前，不是等 catch 结束才析构。
  • 第29行：轮到 catch 执行，输出“捕获: boom”；随后程序继续（第 31 行）。
  • 析构顺序 = 构造顺序的逆序（g1 → g2 → g3），与正常 return 退出时完全一致——栈展开只是把“退出方式”换成了异常。

变体对比

若 inner 里把 throw 换成 return，输出就是：构造 g3、g2、g1 → 析构 g1、g2 → 打印“try 块正常结束” → main 结束时析构 g3。注意 catch 完全不参与。

⚠ 易错点

判断题“catch 处理器执行时，try 块的对象还活着”——错。标准规定：进入处理器前，try 块的自动对象已完成析构。这也正是 RAII 在异常下依然生效的原因。

6. 重新抛出 throw; 与 catch(...) 兜底

示例5：记完日志再 throw;——不吞掉异常

知识点：重新抛出 / catch(...)
#include <iostream>
#include <stdexcept>

double parseRatio(int a, int b) {
    try {
        if (b == 0)
            throw std::invalid_argument("b 为 0");
        return static_cast<double>(a) / b;
    } catch (const std::exception& e) {
        std::cout << "记录日志: " << e.what() << "\n";
        throw;    // 重新抛出“原”异常对象，继续向上传播
    }
}

int main() {
    try {
        parseRatio(3, 0);
    } catch (...) {           // 三个点：接住任何类型的异常
        std::cout << "main 兜底捕获\n";
    }
    return 0;
}
▶ 预期输出
记录日志: b 为 0
main 兜底捕获

逐行解释

  • 第11行：throw;（无操作数）重新抛出正在处理的那个异常对象本身：不复制、不改类型。中间层只做“记日志、补上下文”等本地工作，把决定权留给上层。
  • 第18行：catch (...) 能接住任何类型的异常，但拿不到异常对象（没法调 what()）——通常放在最外层做最后兜底。
  • 本例 catch (...) 在 main 里接住并处理，程序正常 return 0；若 main 里也没人接，就会 std::terminate 异常终止。

变体对比

throw e;（带操作数）会按 e 的静态类型复制一个新异常：本例 e 是 const std::exception&，复制的只有基类部分——派生信息被切片。所以重新抛出永远写 throw;。

⚠ 易错点

catch (...) {} 空着不记日志会把所有错误悄悄吞掉。兜底可以，但要留痕（打日志/上报），处理不了就 throw; 传上去。

7. 异常安全与 RAII：异常路径也要释放资源

栈展开保证局部对象一定被析构，但不保证你手动写的清理代码被执行。于是有了 C++ 的核心纪律 RAII（Resource Acquisition Is Initialization）：把资源交给对象的构造/析构管理——获取即构造，释放靠析构。这样无论正常返回还是异常退出，资源都会被释放。

示例6：裸 new 在异常路径泄漏 vs 局部对象自动析构

知识点：异常安全 / RAII高频考点
#include <iostream>
#include <stdexcept>

struct Guard {                    // RAII 小工具：析构 = 释放
    ~Guard() { std::cout << "Guard 析构：资源已释放\n"; }
};

void risky(bool fail) {
    Guard g;                      // 局部对象：无论从哪退出都会析构
    int* leak = new int[100];     // 裸 new：异常路径没人释放
    if (fail)
        throw std::runtime_error("中途失败");
    delete[] leak;                // 只有正常路径才执行得到
    std::cout << "risky 正常结束\n";
}

int main() {
    try {
        risky(true);
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << "\n";
    }
    std::cout << "leak 指向的内存没人释放——泄漏了\n";
    return 0;
}
▶ 预期输出
Guard 析构：资源已释放
捕获: 中途失败
leak 指向的内存没人释放——泄漏了

逐行解释

  • 第12行 throw 后：栈展开退出 risky——Guard g 被析构（第 1 行输出），但 delete[] leak（第 13 行）被跳过：leak 泄漏，且程序不会报错。
  • “risky 正常结束”不会出现——throw 之后的语句全部跳过。
  • 结论：析构函数是“异常退出时唯一保证执行的清理代码”。资源别手动管，交给对象：内存用 unique_ptr/vector，文件用 fstream，锁用 lock_guard。

变体对比

把第 10 行换成 std::vector<int> data(100);，再运行：泄漏消失——vector 的析构在栈展开时自动释放堆内存。标准容器全是 RAII 类。

⚠ 易错点

判断题“try/catch 会自动释放函数里 new 的内存”——错。catch 只接异常，不管内存；只有对象析构才保证发生。

❌ 裸 new + 手动 delete

void risky(bool fail) {
    int* p = new int[100];
    if (fail)
        throw std::runtime_error("x");
    delete[] p;
    // 异常路径永远到不了
    // delete[] → 泄漏
}

✅ RAII：unique_ptr / 容器

void fixed(bool fail) {
    std::unique_ptr<int[]> p(
        new int[100]);      // <memory>
    if (fail)
        throw std::runtime_error("x");
}   // 无论从哪退出：
    // p 析构时自动 delete[]

8. assert、static_assert 与“错误码 vs 异常”的取舍

示例7：static_assert（编译期）与 assert（调试期）

知识点：断言
#include <iostream>
#include <cassert>    // assert

constexpr int kMaxStudents = 64;

static_assert(kMaxStudents > 0, "班级容量必须是正数");   // 编译期检查
static_assert(sizeof(int) >= 4, "本程序要求 int 至少 32 位");

int main() {
    int count = 30;
    assert(count <= kMaxStudents);   // 运行期（调试）检查：为假才触发
    assert(kMaxStudents == 64);

    std::cout << "运行到这里，说明所有断言都通过了\n";
    return 0;
}
▶ 预期输出
运行到这里，说明所有断言都通过了

逐行解释

  • 第6~7行：static_assert(条件, 消息) 在编译期检查：条件是 false 就直接编译错误，永远生效。它检查的必须是编译期可判定的表达式（常量、sizeof、模板参数等）。
  • 第11~12行：assert(条件) 在运行期检查：条件为假时打印“表达式、文件、行号”等诊断信息并终止程序——具体报错文字因编译器而异，所以示例只演示通过的情形。
  • assert 的开关：定义宏 NDEBUG（发布版常加编译选项 -DNDEBUG）后，assert 变成空语句，完全不参与运行——所以 assert 里绝不能放有副作用的代码（assert(f()); 发布版根本不调用 f）。

变体对比（三兄弟一句话）

static_assert：编译期、永在；assert：运行期、可被 NDEBUG 关闭、用于“内部逻辑自检”；throw：运行期、面向“调用方需要处理的错误”、必须有人接。三者检查的东西不同，不能互相替代。

⚠ 易错点

判断题“assert 失败会抛出异常被 catch 接住”——错。assert 失败直接终止程序（不经过任何 catch）；它是给程序员看的，不是给用户看的。

错误码 vs 异常：怎么取舍？

返回错误码异常
会被忽略吗会（调用方不检查也没人管）不会（不接住就 terminate）
正常路径开销零几乎零（抛出时才有开销）
能穿过多层调用直达处理点不能（层层传递）能（自动沿调用链上传）
构造函数能用吗不能（没有返回值）能（抛异常是标准做法）
适合预期内、常见的失败异常的、本地处理不了的失败

9. 构造函数抛异常与析构函数的纪律

构造函数没有返回值，报告失败的唯一手段就是抛异常。关键规则：构造函数抛出异常 → 对象“从未构造完成” → 它自己的析构函数不会被调用；但已构造完成的成员会按逆序析构。

示例8：构造函数抛异常——成员被析构，自身析构不执行

知识点：构造与异常高频考点
#include <iostream>
#include <stdexcept>
#include <string>

struct Member {
    std::string name;
    explicit Member(std::string n) : name(n) {
        std::cout << "构造 Member(" << name << ")\n";
    }
    ~Member() { std::cout << "析构 Member(" << name << ")\n"; }
};

class File {
public:
    File() : member("File 的成员") {
        std::cout << "File 构造函数开始执行\n";
        throw std::runtime_error("磁盘已满，打开失败");
    }
    ~File() { std::cout << "析构 File\n"; }   // 注意：不会执行
private:
    Member member;
};

int main() {
    try {
        File f;
        std::cout << "这行不会执行\n";
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << "\n";
    }
    return 0;
}
▶ 预期输出
构造 Member(File 的成员)
File 构造函数开始执行
析构 Member(File 的成员)
捕获: 磁盘已满，打开失败

逐行解释

  • 构造顺序：先构造成员 member（第 1 行输出），再执行 File 的构造函数体（第 2 行输出）。
  • 第17行 throw 后：File 对象没有诞生——所以 ~File()（第 19 行）不会执行，输出里没有“析构 File”。
  • 但已构造完成的成员 member 会被栈展开析构（第 3 行输出）。这就是为什么成员应尽量用 RAII 类型（string、vector、智能指针）：构造中途失败也不会泄漏。
  • 第27行：File f; 这行没完成，其后的 cout 被跳过；异常交给 catch。

变体对比

若把 throw 挪到“成员构造之前”是不可能的——成员先于构造函数体执行。正因如此，把资源获取写进成员的构造函数（而不是 File 自己的函数体）才天然异常安全。

⚠ 易错点

判断题“构造函数抛异常后析构函数也会被调用，负责善后”——错。对象没构造完成就没有析构；善后靠的是“已构造成员的析构”，这要求成员本身是 RAII 的。

析构函数的纪律（一句话）：不要让异常逃出析构函数——若栈展开途中又有异常抛出，程序直接 std::terminate。析构里的清理代码自己处理好错误（记录、忽略），绝不 throw。

10. noexcept 与异常规范的演变

异常规范（exception specification）= 给函数标注“能抛什么”。历史上换过两套写法，旧的一套（动态异常规范）已被 C++17 移除。

示例9：noexcept 标注不抛异常

知识点：noexceptC++11
#include <iostream>

void log_line() noexcept {          // 承诺：这个函数绝不抛异常
    std::cout << "log: ok\n";
}

int main() {
    log_line();
    static_assert(noexcept(log_line()), "log_line 应是 noexcept");  // 编译期验证承诺
    std::cout << "main 正常结束\n";
    return 0;
}
▶ 预期输出
log: ok
main 正常结束

逐行解释

  • 第3行：noexcept 是 C++11 的“不抛承诺”，写在编译期就能查证（noexcept(表达式) 运算符返回 true/false，第 9 行用它配合 static_assert 做编译期验证）。
  • 违反承诺的后果：noexcept 函数若真的把异常抛出去（没在函数内部接住），不是“可捕获的异常”，而是直接 std::terminate 终止程序：
// 片段（不要这样做）：
void f() noexcept {
    throw std::runtime_error("逃逸");   // 编译能通过；运行时 → std::terminate
}
  • 为什么值得标注：标准库靠它做优化（如 vector 扩容时，移动构造是 noexcept 才敢用移动而不是拷贝——第 9 章 move 语义的伏笔）。

变体对比

noexcept(false) 表示“可能抛出”（普通函数默认即如此）；C++11 起析构函数默认就是 noexcept(true)——所以“析构中抛异常”几乎必然 terminate。

⚠ 易错点

判断题“noexcept 函数抛出的异常会被外层 catch 接住”——错。违反 noexcept 不走 catch，直接 terminate。承诺前先确认函数真的不抛。

11. 综合示例

示例10：异常穿过中间层——底层抛、调用方接、程序不断

综合
#include <iostream>
#include <stdexcept>
#include <vector>

// 查询函数自己不处理错误：把异常留给调用方决定
int queryScore(const std::vector<int>& scores, std::size_t idx) {
    return scores.at(idx);
}

int main() {
    std::vector<int> scores = {90, 85, 77};

    for (int idx : {0, 5}) {
        try {
            std::cout << "查询成功: " << queryScore(scores, idx) << "\n";
        } catch (const std::out_of_range&) {
            std::cout << "下标 " << idx << " 越界\n";
        } catch (const std::exception&) {
            std::cout << "其他异常\n";
        }
    }
    std::cout << "程序正常结束\n";
    return 0;
}
▶ 预期输出
查询成功: 90
下标 5 越界
程序正常结束

逐行解释

  • 第6~7行：queryScore 用 at() 而不是 []——越界时抛 out_of_range，把“怎么处理”交给调用方（这正是 at 存在的意义）。
  • 第14行：第一圈 idx=0，正常返回 90。
  • 第二圈 idx=5：at 抛异常，异常穿过 queryScore 的栈帧直达 catch，输出“下标 5 越界”。每个元素处理完，循环继续——单次失败不拖垮整个流程。
  • catch 里打印的是固定消息；若打印 e.what()，文字因编译器而异（第 4 节讲过）。

变体对比

若把两个 catch 的顺序对调（exception 在前），越界也会被基类接走，输出变成“其他异常”——再次验证“自上而下第一个命中”。

⚠ 易错点

“抛异常的程序都会崩溃”——错。只要有人接住并处理，程序照常继续；崩溃只发生在“无人捕获 → terminate”时。

13. 常见错误

1. 按值捕获基类：catch (std::exception e) 复制一份基类对象 → 对象切片，派生信息丢失、多态失效。修复：catch (const std::exception& e)。
2. 基类 catch 写在派生类前面：异常被基类分支截走，派生类分支成死代码（编译器常给“永远不会匹配”警告）。专精的 catch 在前，兜底的 exception 在最后。
3. 异常路径资源泄漏：throw 跳过 delete/fclose。修复：RAII——unique_ptr、vector、fstream、lock_guard 托管一切资源。
4. 用 throw e; 重新抛出：按 e 的静态类型复制，可能切片并丢失原异常。修复：无操作数的 throw;。
5. 在析构函数中让异常逃出：栈展开中再抛异常 → std::terminate。析构函数（默认 noexcept）里的清理代码必须自己处理错误。
6. 用异常当控制流：循环里靠抛异常代替 if 判断——又慢又难读。异常留给“异常的”情况；预期内的分支用返回值/if。

更多同类错误见 编译错误博物馆（如 “unresolved external symbol terminate”），以及 考试易错点 中的“栈展开顺序”专题。

老教材出现的 throw(std::bad_alloc) 这类写法在 C++17 起无法编译；看到 throw() 要按 noexcept 理解。判断题“动态异常规范直到今天仍在使用”——错，C++17 已移除。

本章小结

异常 = 沿调用链向上投递的错误对象：throw 即中断，catch 按类型自上而下取第一个命中；栈展开让沿途局部对象按构造逆序析构（try 块对象在 catch 前析构）。RAII 是异常安全的基石——只要资源长在对象上，异常路径也会被释放。
  • 捕获一律 const std::exception&：无切片、支持 what() 多态；派生类 catch 在前，基类兜底在后。
  • 标准层次：exception → logic_error（invalid_argument / out_of_range / length_error）、runtime_error；自己抛的消息确定，标准库的 what() 文本因实现而异。
  • 重新抛出用 throw;；catch (...) 只能兜底、拿不到对象。
  • 构造函数抛异常 = 标准做法：自身析构不调用、已构造成员被析构；析构函数绝不抛。
  • assert（调试期、NDEBUG 可关）、static_assert（编译期、永在）、noexcept（不抛承诺，违反即 terminate）各司其职。
  • 无人捕获 → std::terminate；错误码适合常见小错，异常适合“本地处理不了的失败”。

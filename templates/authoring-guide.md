# Chapter Authoring Guide

This site is a **fully offline** static teaching website: HTML5 + CSS3 + vanilla JavaScript, with no CDN, no web fonts, no images and no `fetch()`. Every page must open by double-clicking it over `file://`.

This guide defines the canonical markup for every reusable component. The site copy is Chinese, but developer-facing documentation and code comments are English-only.

## 0. Hard Rules

1. **Escape code block content**: `<` must be written as `&lt;`, `>` as `&gt;`, and `&` as `&amp;` inside `<pre><code>`. For example, `#include <iostream>` must be written as `#include &lt;iostream&gt;`. The validator treats a raw `<iostream>` as an unknown tag.
2. **JSON data blocks must be strict JSON**: no comments, no trailing commas, double quotes only, and embedded double quotes escaped as `\"`.
3. **No external resources**: no HTTP(S) assets, CDN, web fonts or images. Do not use `fetch` or `import`.
4. **Do not edit shared assets or other chapters** unless that is your assigned task.
5. **UTF-8** for every file. Write the Chinese site copy normally.
6. **Expected output must be correct.** If you are not sure, do not invent it; trace the example against standard C++ first.
7. **Undefined behaviour (UB) is never a "predict the output" question.** Every UB example must use `<div class="ub-warning">...</div>` and explain why it is UB (uninitialized read, `i = i++ + 1`, out-of-bounds access, dangling reference, and so on). Compiler-specific differences use `<div class="std-diff">`.
8. **Every example card must contain complete, compilable code** with `#include` and `main`, unless the card is intentionally a "wrong code" example. Wrong-code examples still use `<pre><code class="cpp">` and the same escaping rules.

## 1. Page Skeleton

Start a new chapter from `templates/chapter-template.html`. Key points:

- `<head>`: UTF-8, viewport, `<title>Chapter N ... | College C++ Offline Assistant</title>`, the theme bootstrap script, and `<link rel="stylesheet" href="../assets/css/style.css">`.
- The body contains one `<main class="container chapter">`. Its sections are, in order:
  1. **Objectives**: `<section class="card objectives">` with a short prerequisite line.
  2. Body sections: several `<h2>` headings with example cards and interactive widgets.
  3. **Common errors**: `.warn`, `.ub-warning` and comparison blocks.
  4. **Standard differences**: `.std-diff`, either here or inline in the body.
  5. **Summary**: `<div class="keypoint">` plus a short bullet list.
  6. **Self-check**: `<ul class="checklist" data-chapter="chXX">`.
  7. **Quiz**: `<section class="quiz" data-source="chXX">`.
- The validator requires three literal section labels and one quiz section. Copy them from the template; do not translate or rename them.
- After `</main>`, load the classic scripts in the template order (`highlight.js`, `toc.js`, `nav.js`, `quiz.js`, `interactive.js`, `teacher.js`, `mastery.js`). v2 pages also load `v2-config.js`, `v2-core.js` and `v2-lab.js`; the injection helper adds these.
- The header, footer and previous/next pager are generated by `nav.js`. Do not hand-write them.
- Keep all widget JSON inside the body at the relevant position.

## 2. Example Cards (8-15 per chapter)

```html
<article class="example-card" id="ch02-ex-01">
  <div class="ex-head">
    <h3 class="ex-title">Example 1: Prefix vs postfix increment</h3>
    <div class="ex-meta"><span class="tag">Topic: increment</span><span class="tag amber">High-frequency exam point</span></div>
  </div>
  <pre class="ex-code"><code class="cpp">#include &lt;iostream&gt;
int main() {
    int i = 5;
    std::cout &lt;&lt; i++ &lt;&lt; "\n";   // reads the old value first
    std::cout &lt;&lt; i   &lt;&lt; "\n";
    return 0;
}</code></pre>
  <div class="ex-btns"></div>
  <div class="ex-output">
    <div class="ex-output-label">Expected output</div>
    <pre><code class="output-text">5
6</code></pre>
  </div>
  <div class="ex-explain">
    <h4>Line-by-line explanation</h4>
    <ul>
      <li><b>Line 4</b>: ...</li>
    </ul>
  </div>
  <div class="ex-variants">
    <h4>Variants</h4>
    <p>Changing <code>i++</code> to <code>++i</code> prints 6 and 6.</p>
  </div>
  <div class="ex-pitfall">
    <h4>Common mistake</h4>
    <p>...</p>
  </div>
  <script type="application/json" class="ex-steps">{ "steps": [
    { "line": 3, "vars": { "i": "?" }, "out": "", "note": "..." },
    { "line": 5, "vars": { "i": "5" }, "out": "5", "note": "..." }
  ] }</script>
</article>
```

Rules:

- `id` is required and must be unique on the page: `chXX-ex-NN`.
- Keep the empty `.ex-btns` container if you want a stable toolbar position; if omitted, the engine inserts one.
- `.ex-output` starts hidden. Its content goes inside `<pre><code class="output-text">`.
- `.ex-explain` is required; `.ex-variants` and `.ex-pitfall` are strongly recommended. Omit empty sections.
- `.ex-steps` should be present in at least two cards per chapter. `line` is the physical line number in the code block (1-based); `vars` is the variable snapshot after the step (string values); `out` is the new console line for that step (`""` if none); `note` is the explanation.
- Short demonstration snippets may omit `main`, but the explanation must say it is a fragment. Examples with output should be complete and compilable.

## 3. Interactive Components

### 3.1 Side-by-side comparison (HTML only)

```html
<div class="compare">
  <div class="compare-col badc"><h4>Common wrong version</h4> ... </div>
  <div class="compare-col good"><h4>Recommended version</h4> ... </div>
</div>
```

### 3.2 Memory visualization

```html
<div class="memviz"><script type="application/json" class="mem-data">{ "title": "int a = 42; int* p = &amp;a;",
  "regions": [
    { "addr": "0x7ffe...1000", "name": "a", "type": "int", "value": "42", "note": "stack object" },
    { "addr": "0x7ffe...2008", "name": "p", "type": "int*", "value": "0x7ffe...1000", "note": "p stores the address of a" }
  ],
  "note": "p points to a" }</script></div>
```

`<script type="application/json">` content is raw text, so JSON values may contain `vector<int>` and `int*` directly. The only forbidden sequences are `</script>` inside a string and invalid JSON (comments, trailing commas). Components escape values for display; do **not** write HTML entities inside `ex-steps`, `mem-data` or `sort-data`. Quiz `q` and `explain` fields are inserted as HTML, so literal `<` there must be written as `&lt;`.

### 3.3 Drag-to-sort

```html
<div class="widget-sort"><script type="application/json" class="sort-data">{ "items": [
  "line 1 (correct first line)", "line 2", "line 3"
], "hint": "Optional hint", "explain": "Shown after a correct check" }</script></div>
```

Write `items` in the correct order. The engine shuffles them and supports drag-and-drop plus up/down buttons for touch devices.

### 3.4 Increment/decrement animation

```html
<div class="widget-incdec" data-start="5"></div>
```

### 3.5 Callout blocks

- `<div class="note">` - supplementary note.
- `<div class="tip">` - practical tip.
- `<div class="warn">` - warning.
- `<div class="ub-warning">` - undefined behaviour; the heading is added automatically.
- `<div class="std-diff">` - standard-version difference; the heading is added automatically.
- `<div class="keypoint">` - key conclusion.

### 3.6 Folded answer

```html
<details class="fold"><summary>Show answer</summary><div class="details-body">...</div></details>
```

### 3.7 Self-check list

```html
<ul class="checklist">
  <li><label><input type="checkbox"><span>Explain the order of value read and increment in i++ and ++i</span></label></li>
</ul>
```

`mastery.js` replaces the checkboxes at runtime with know/don't-know buttons and stores the state in localStorage. Authors only need the markup above.

### 3.8 Quiz

```html
<section class="quiz" data-source="ch02">
  <script type="application/json" class="quiz-data">{ "title": "Quiz: operators",
    "questions": [
      { "type": "mcq", "q": "Given int i = 3; what does cout << i++; print?",
        "options": ["3", "4", "compile error", "undefined"], "answer": 0,
        "explain": "i++ returns the old value 3." },
      { "type": "tf", "q": "++i is always faster than i++.", "answer": false,
        "explain": "For built-in types there is no difference on modern compilers." },
      { "type": "fill", "q": "The value of 7 / 2 is ____.", "answer": ["3"], "explain": "Integer division truncates toward zero." },
      { "type": "code", "q": "Complete the loop: for (int i = 0; i ____ 10; ++i)", "answer": ["<"], "explain": "..." }
    ] }</script>
</section>
```

- `data-source` is the chapter id (for example `ch02`); the review bank uses it.
- Use 6-10 questions per chapter; at least four should be multiple choice, mixed with true/false, fill-in and code.
- `q` may contain HTML such as `<code>x</code>`, but literal `<` inside code must be escaped.
- Never use UB as the standard answer to a quiz question.

### 3.9 Bug hunt

Usually no markup is needed: if `assets/js/bughunt-data.js` contains exercises for the chapter, `bug-hunt.js` inserts the bug-hunt section before the quiz. To control the position manually:

```html
<section class="bug-hunt" data-ch="ch02"></section>
```

- `data-ch` is the chapter id; omit it or use `all` for every exercise. Add `data-shuffle="1"` for a shuffle button.
- Exercise fields: `id`, `ch`, `title`, `kind` (`compile` / `logic` / `ub`), `code` (one raw string per line), `bugLine`, optional `hint`, and `why` (raw HTML).
- Code lines are raw text; the engine escapes and highlights them. `why` is inserted as HTML, so angle brackets must be entities.
- UB exercises never ask for a deterministic output; explain the cause instead.

### 3.10 Parsons problem

```html
<div class="widget-parsons"><script type="application/json" class="parsons-data">{ "title": "Rebuild the skeleton",
  "items": [
  "class Foo {",
  "public:",
  "..."
  ], "hint": "Optional hint", "explain": "Shown after a correct check" }</script></div>
```

- `items` is the correct code order as plain text (indentation preserved with spaces).
- Interaction: drag from the shuffled pool into the program area; reorder with drag or up/down; send a line back with the X button; "Check order" reports the first wrong line.
- Five to ten lines works best. Duplicate lines are allowed; grading is by position.

### 3.11 Pointer diagram

```html
<div class="widget-ptrviz"><script type="application/json" class="ptrviz-data">{ "title": "...",
  "vars": [ { "name": "a", "type": "int", "value": "42" }, { "name": "p", "type": "int*" } ],
  "frames": [
    { "ptrs": { "p": "a" }, "note": "p points to a" },
    { "ptrs": { "p": "null" }, "note": "p is null" },
    { "ptrs": { "p": "local" }, "freed": ["local"], "note": "local is gone; p dangles (red dashed arrow)" }
  ] }</script></div>
```

- `vars` is the set of boxes (wrapped after six boxes); each frame has `ptrs` (pointer name to target name or `"null"`), `freed` (names destroyed in this step; boxes get a strikethrough) and `note`.
- **The field must be named `frames`**, not `steps`; the validator treats `ex-steps`' `steps` as stepper data and checks its `line` fields.
- Good topics: address assignment, two pointers, reassignment, nulling, dangling pointers with `freed`.

### 3.12 Multi-blank code quiz (`mfill`)

```html
{ "type": "mfill", "q": "Complete the swap.",
  "code": "int t = a;\na = ____;\nb = ____;",
  "blanks": [ { "answer": "b" }, { "answer": "t" } ],
  "explain": "..." }
```

- Each `____` (four or more underscores) maps to `blanks[i]` in order; the counts must match (the validator checks this).
- `answer` may be a string or an array of accepted answers; `ci: true` makes matching case-insensitive. Each blank is graded independently.
- To make an example card runnable, no extra markup is needed: cards with `int main` and without unsupported syntax automatically show the "Run online" button. The teaching-subset interpreter stops with an explanation on UB instead of inventing output.

### 3.13 v2 explainer (optional)

If the chapter is also copied to `v2/chapters/`, an explainer can be attached to one example card. Add a `demo` object to `V2_CONFIG.chapters.chXX` in `v2/assets/js/v2-config.js`:

```js
demo: {
  cardId: "ch05-ex-04",
  engine: "scene",
  question: "How far does pointer arithmetic move?",
  frames: [ /* one picture per step */ ]
}
```

Supported engines: `memory`, `stack`, `timeline`, `scene`, `grid`, `bars`. Use `useStepStack: true` or `useStepBars: true` to reuse existing `ex-steps` data. The explainer starts paused and prints its final frame. See `v2/README.md` for the frame schemas.

## 4. Text and Layout Conventions

- Heading hierarchy: `<h2>` for sections, `<h3>` for example titles (already inside the card).
- Inline code uses `<code>...</code>` with internal escaping.
- Tables use `<table class="data-table">`.
- Bold a term the first time it is defined.
- Write for a one-semester university course: concise, point-first, avoid long prose.

## 5. Pre-Submit Checklist

- [ ] Every `<`, `>` and `&` inside code blocks is escaped.
- [ ] Every JSON block parses with `JSON.parse` (no comments, no trailing commas).
- [ ] Example ids are unique (`chXX-ex-NN`).
- [ ] 8-15 example cards; at least two cards have `.ex-steps`.
- [ ] Quiz has 6-10 questions; checklist has 6-8 items.
- [ ] The chapter has the common-errors, standard-difference and summary sections.
- [ ] Every UB case uses `.ub-warning` and is not used as a quiz answer.
- [ ] `node tools/validate.js chapters/chXX-xxx.html` passes.
- [ ] If the chapter was copied to v2, `node v2/tools/validate-v2.mjs` also passes.
